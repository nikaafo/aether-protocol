                 Aether: A Next-Generation L4 Transport
                draft-veronikafomich-aether-protocol-00

Abstract

   This document specifies Aether, a transport-layer protocol (L4)
   designed for modern network environments requiring multiplexed
   streams without head-of-line blocking, mandatory encryption with
   post-quantum resistance, multi-path routing, and self-sovereign
   identity at the protocol layer.  Aether operates entirely in
   userspace without kernel modifications.

1.  Introduction

1.1.  Motivation

   Transport-layer protocols have evolved slowly.  TCP (RFC 9293)
   provides reliable, ordered delivery but suffers from head-of-line
   blocking and requires separate TLS for encryption.  UDP (RFC 768) is
   lightweight but unreliable.  QUIC (RFC 9000) addresses many of
   TCP's shortcomings but is tightly coupled to HTTP/3.

   Aether is a general-purpose L4 transport protocol designed for:

   o  Stream multiplexing without head-of-line blocking
   o  Mandatory encryption with post-quantum resistance
   o  Multi-path connections (seamless network switching)
   o  Self-sovereign identity at the protocol layer
   o  Userspace operation (no kernel modifications required)

1.2.  Design Philosophy

   +=========================+=======================================+
   | Principle               | Application in Aether                 |
   +=========================+=======================================+
   | Simple core             | Fixed 16-byte base header; features   |
   |                         | via extensions                        |
   +-------------------------+---------------------------------------+
   | Security non-optional   | AEAD encryption from first packet;    |
   |                         | no plaintext mode                     |
   +-------------------------+---------------------------------------+
   | Versioning              | First packet declares version and     |
   |                         | capabilities                          |
   +-------------------------+---------------------------------------+
   | Self-describing         | Protocol metadata embedded in         |
   |                         | handshake                             |
   +-------------------------+---------------------------------------+
   | Userspace-first         | No OS kernel modifications required   |
   +-------------------------+---------------------------------------+

3.2.  ClientHello

   CBOR-encoded, inside AEAD-encrypted Initial packet payload:

   {
     "ver": 0,
     "cid": <64-bit random client CID>,
     "supported_versions": [0],
     "crypto": {
       "kem": "Kyber768",

       "hash": "SHA-256"
     },
     "capabilities": {
       "multipath": true,

       "max_stream_data": 1048576,
       "ack_frequency": 2,
       "idle_timeout_ms": 30000
     },
     "identity": {
       "type": "ed25519",
       "public_key": <32-byte Ed25519 public key>
     },
     "extensions": []
   }

3.4.  Key Derivation

   After ClientHello and ServerHello exchange:

   shared_secret = Kyber768.Decapsulate(kem_ciphertext)
                   || X25519.DH(client_ephemeral, server_classical_pk)

   transcript = ClientHello || ServerHello

   session_key = HKDF-Expand(
       HKDF-Extract("AETHER-v0", shared_secret),
       transcript,
       256 bits
   )

   client_tx_key = HKDF-Expand(session_key, "client-tx", key_len)
   server_tx_key = HKDF-Expand(session_key, "server-tx", key_len)

   After key derivation, ClientFinished and ServerFinished carry:

   {
     "finished": HMAC-SHA256(session_key, transcript)
   }

   Symmetric keys are destroyed after 3x PTO following connection
   close, providing Perfect Forward Secrecy.

4.  Streams

   o  Each stream identified by 18-bit Stream ID (0..262143).
   o  Stream ID 0 reserved for control.
   o  Client opens streams with EVEN IDs; server with ODD IDs.
   o  Streams are independent: loss in one stream does not block
      others.

   Stream lifecycle:

              Frame: StreamOpen
   IDLE  ---------------------------->  OPEN
                                           |
                                           | Frame: Data / Ack
                                           v
              Frame: StreamClose (FIN)
   OPEN  ---------------------------->  HALF-CLOSED
                                           |
                                           v
              Frame: StreamClose (ACK)
   HALF-CLOSED ---------------------->  CLOSED

                   Figure 5: Stream State Machine

   Flow control operates at two levels:

   o  Connection-level: total in-flight data for the connection.
   o  Stream-level: in-flight data per stream.

   Initial windows (negotiated in Capabilities):
   o  Stream flow control window: 1 MiB (1,048,576 bytes).
   o  Connection flow control window: 16 MiB (16,777,216 bytes).

   Each Data packet carries an Offset (byte position in stream).
   Receivers send Ack frames with received offset ranges.
   Unacknowledged packets are retransmitted with exponential back-off
   up to MAX_RETRANSMISSIONS (10).

5.  Multi-Path

   Connections are identified by Connection ID, not IP address.
   This enables path migration:

   1.  Client detects a new network interface (e.g., 5G after Wi-Fi).
   2.  Client sends PathChallenge from new IP to server.
   3.  Server responds with PathResponse, confirming the new path
       belongs to the same connection.
   4.  Server begins sending data on both paths.
   5.  Client may duplicate data on both paths for reliability.

   Each path has a unique Path ID (Extension Type 0x04).
   Packets from different paths are multiplexed onto common streams;
   the receiver reassembles by Offset.

   When one path is lost, data automatically flows through remaining
   paths without connection interruption.

6.  Congestion Control

   The default congestion control algorithm is Aether-CC, a hybrid
   of BBRv3 [BBR] and NewReno [RFC6582], optimized for:

   o  High-latency satellite links
   o  Variable-bandwidth mobile networks
   o  Noisy channels (distinguishing loss from congestion)

   Bandwidth estimation:

   delivery_rate = bytes_acked / time_delta
   max_bw = max(max_bw, delivery_rate)

   RTT estimation:

   min_rtt = min(min_rtt, latest_rtt)  // over 10-second window

   Congestion window:

   cwnd = max_bw * min_rtt * gain
   // gain: 1.25 during probing, 0.75 during drain

   Loss classification:
   o  Loss with low RTT and rising delivery_rate -> congestion
   o  Loss with high RTT and stable delivery_rate -> channel noise
      (do not reduce window)

   Pluggable algorithms (negotiated via Capabilities):
   o  "aether-cc" (default)
   o  "bbrv3"
   o  "cubic"
   o  "none" (testing)

7.  Security Considerations

   Aether has no plaintext mode.  All packets are encrypted:

   o  Initial packets: AEAD with key derived from initial salt.
   o  Handshake packets: AEAD with keys derived from shared_secret.
   o  Data packets: AEAD with session_key.

   The handshake uses Kyber-768 [FIPS203] as primary KEM with X25519
   [RFC7748] as classical fallback, providing post-quantum resistance
   as long as at least one algorithm remains secure.

   Metadata protection:

   o  Connection ID in short header is a 32-bit truncated value.
   o  Padding extension (0x03) allows random bytes for packet size
      obfuscation.
   o  Multipath data streams complicate passive traffic analysis.

   Each connection generates ephemeral keys.  Compromise of an
   identity key does not reveal past sessions (Perfect Forward
   Secrecy).

8.  Identity Layer

   Aether introduces cryptographic identity at the transport layer.
   Each node has an Ed25519 [RFC8032] key pair.  Identity is:

   identity = SHA-256("AETHER-ID-" || Ed25519_public_key)

   During handshake, the node proves key ownership by signing the
   transcript.

   Advantages over existing identity models:

   o  DNS/CA/PKI independent — self-sovereign identity.
   o  IP mobility: IP changes do not affect identity.
   o  Decentralized: no central registry required.
   o  W3C DID compatible: identity representable as a DID.

9.  Connection Close

   Graceful close:

   Sender   -> Close (code: 0x00 "NO_ERROR")
   Receiver -> Close (code: 0x00 "NO_ERROR")
   Connection closed -> keys destroyed after 3x PTO

10.  Discovery

   Local discovery (LAN):

   o  Multicast group: 224.0.0.251:9000 (IPv4), ff02::fb:9000 (IPv6).
   o  Periodic announcements every 30 seconds.
   o  Announcement format: Initial packet with type "Announce" in
      extensions.

   Global discovery (WAN):

   o  Kademlia-based DHT (as in libp2p).
   o  DHT key = peer identity.
   o  DHT value = set of (IP, port, Connection ID) tuples.

   Enables peer location by identity without a centralized server.

Appendix A.  Reference Implementation

   A reference implementation of Aether Protocol v0.1 is available
   in the Rust programming language at:

   https://github.com/nikaafo/aether-protocol

   Components:
   o  aether-core: Protocol library (framing, handshake, crypto,
      multipath, congestion control, identity, discovery).
   o  aether-sdk: Enterprise SDK (identity vault, monitoring, SLA).
   o  aether-gateway: L4 proxy for Aether-to-TCP bridging.
   o  demo: Example application.

   License: MIT OR Apache-2.0.
